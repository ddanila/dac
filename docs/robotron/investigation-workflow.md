# Simulation-to-bench investigations

## Record and replay an experiment

Enable **Record next session from power-on** before starting the classic machine.
The worker records input, reset, capture and disk-export operations at their applied
CPU clocks. **Record checkpoint** hashes registers, RAM, text memory, the disk
image and diagnostics without flushing pending writes. Recording is bounded to
120 simulated seconds and 10,000 actions; exceeding either invalidates export.

**Export investigation** downloads a `.p1715investigation` JSON archive. Initial
ROM/disk bytes are omitted unless **Include initial ROM and disk** is selected.
Completed capture bytes and their metadata are included when available. The file
can therefore contain observed ROM bytes even when the full initial ROM is omitted.
Review the input-inclusion choice before sharing private media.

Open the bundle, power off, then choose **Replay from boot**. Referenced inputs
must match their hashes or be explicitly included in the bundle. Replay verifies
the JavaScript and WASM engine identities, finishes paused and stops at the first
checkpoint mismatch. **Replay until** can select an earlier checkpoint; this
reruns from boot rather than restoring an incomplete machine snapshot. Cancel
leaves the partially replayed machine paused. Editing is disabled during replay.

The analyzer also imports and exports these bundles, including both captures,
metadata, assertion rules, cursor ranges and reports. Analyzer-only bundles are
view-only. Original reports survive export separately; run assertions again for
fresh results. Inputs are not executed merely by importing an archive. Both file
names and contents are validated, with a 128 MiB decoded archive limit.

Native replay uses Pico1715's `tools/browser/replay.mjs`. Explicit engine rebinding
requires the same clean source revisions and records both identities. See
[experiment format and CLI](https://github.com/ddanila/Pico1715/blob/main/docs/experiments.md).

## Capture and analyze

**Trace to source** loads the bundled CP/M platform/diagnostic profiles or a local
hash-bound ZMAC source map with its matching binary. Select a fetch or find a
symbol's first observed fetch. The result separates observed bytes/disassembly
from image bytes and source lines. Missing operands, uncertain intervals and an
unknown low-memory ROM overlay cannot establish a verified instruction. A matching
source candidate is not proof of image residency or instruction completion.
Loaded source material accompanies explicit investigation-bundle export.

The initial source generator supports the platform and diagnostic ZMAC listings;
relocatable RMAC BIOS source mapping remains a follow-up. Source scanning is
bounded to two million preceding records and can be cancelled.

The classic workstation's **Bus capture → analyzer** controls use the same passive
cycle encoder RTL as the native capture oracle. Both controller-model and shared
firmware/RTL backends support manual capture, capture-from-reset, stop, release,
download and direct handoff to the standalone analyzer. No extra emulator loads
inside the analyzer page.

Default capture is I/O + IACK + reset, 16 MiB, with no simulated-time limit. Choose
full bus for opcode/memory milestones, up to 64 MiB and optionally 120 simulated
seconds. Large full-bus recordings can fill before a boot completes: use the native
runner's later start window, or capture a shorter interactive operation. Reaching
a limit stops acquisition and drains the encoder without stopping the guest.
Pause and step retain simulated-clock semantics. The sidecar distinguishes reset
requests from sampled CPU reset: there is no fabricated reset pulse.

Open in analyzer uses an explicit same-origin, one-use nonce handshake. Captures
and bounded metadata are transferred in memory; ROMs/disks are not transferred or
persisted automatically. Popup restrictions can be handled by downloading the
`.p1715` and `.metadata.json` files and opening them manually. Shutdown of the
simulator worker discards its unsaved capture.

## Boot investigation

Profiles are generated by `node scripts/build-boot-profiles.mjs` from current
CP/M outputs and existing exact-hash stock qualification records. Regenerate after
changing the bundled disk. Public fixture, reference-ROM CP/M 3 and qualified SCP
0006 inputs have distinct profiles. The public fixture bypasses the historical
bootstrap. A hash mismatch, or writes before capture, prevents qualification of a
selected profile. Unknown inputs retain generic controller annotations.

Stages link to actual capture record numbers or timestamped console/reset
observations. Execution-address stages need full-bus capture. Console observations
are sampled text memory, not CRT timing or proof of the physical display. A fetch
alone never establishes boot success. Missing evidence stays unavailable or not
reached within the recorded window; it is not a guessed failure location.

Select a stage range, then select the corresponding range in the reference pane.
**Compare range → Both cursor ranges** retains strict existing I/O semantics,
including unequal-tail failures. There is no automatic resynchronization. Reports
include capture hashes, profile identities, evidence, assertion rules/results and
comparison settings. Capture bytes must be saved separately.

## Assertions in browser and CI

The worker and Node CLI import one pure JS engine. Built-ins cover controller CRC
integrity, the original session smoke program, modeled interrupt/watchdog bounds
and diagnostic guest storage traffic. The 81.92 µs watchdog envelope is a model
contract; it is not measured hardware timing. Guest traffic does not prove file
contents: the guest/host diagnostic oracle verifies those separately.

Upload a schema-1 JSON suite or use a built-in. For example:

```json
{
  "schema": 1,
  "id": "example-handshake",
  "revision": 1,
  "rules": [
    {"id":"request-seen","type":"count","event":{"kind":"io_write","address":3},"min":1},
    {"id":"response","type":"response","event":{"kind":"io_write","address":3},"response":{"kind":"interrupt_ack"},"within_us":20}
  ]
}
```

This example's 20 µs is an illustrative scenario bound, not a stock-OS requirement.
Supported types are count (min/max; max zero forbids), ordered sequence (`events`),
response (`event`, `response`, `within_us`) and bound (`event`, `field` duration_us
or wait_us, `max`). Matchers require a kind and optionally address/data masks or a
literal annotation substring `note`. I/O address matching defaults to the low byte.
Responses satisfy pending requests one-to-one, oldest first, strictly after their
trigger. No trigger or an unfinished deadline is inconclusive. Other rules judge
only the explicitly selected recording window, not an unrecorded future.

Loss, partial/unstable/saturated events and uncertain decoder annotations prevent
passing conclusions. Filtered-out required event classes are inconclusive; raw
files are not applicable. Results keep at most 32 evidence indexes per rule; suites
allow 128 rules, 64 sequence steps and 4096 outstanding requests per response rule.
A 20-million-operation work bound prevents unbounded analysis; exceeding it yields
inconclusive results. Cancellation remains available.

```
node tools/analyzer/check.mjs capture.p1715 suite.json report.json
node tools/analyzer/check.mjs capture.p1715 suite.json report.json 100 500
```

Ranges are zero-based, start-inclusive/end-exclusive. `-` uses the default suite
or stdout. Reports are created exclusively. Exit 0 means every required rule
passed; 1 means a nonpassing result; 2 means invalid inputs or an execution error.
There is no separate Python assertion interpreter.

## Reproducible demonstration

1. Build Pico1715 session libraries using `tools/build_browser.py --native`.
2. Build the source CP/M 3 image with `make all test-rom`.
3. Use Pico1715 `tools/capture_session.py` with the model library, source-built
   fixture ROM/image, `--clocks 40000000` and a new output directory.
4. Open the resulting capture and metadata in the analyzer; the I/O-only view
   observes controller reads and console prompt while correctly marking fetch
   milestones unavailable. Run the controller-integrity suite.
5. Use `P1715TST W`, cold boot and `P1715TST R` on a disposable working image.
   `cpm-plus-1715/tools/check_diagnostics.py` automates guest and independent host
   checking, including corruption and collision cases.
6. Rehearse Pico1715's `tools/bringup.py` in simulated mode, attach its explicitly
   simulated stage evidence, and replay/download the capture. Run the same
   assertions and export the artifact directory for independent review.

No simulation or completed software report qualifies actual USB throughput,
connector mechanics, bus levels, SD durability or reserve power. The bring-up
runner preserves those physical stages as pending until operator evidence exists.

## Scheduled fault experiments

The workbench's **Reproducible investigation** panel can start a bounded fault
experiment from boot. Select CRC corruption, a dropped byte, controller delay,
absent media or read-only mounting; the firmware backend additionally supports
SD delay, next-write failure and a queued power-fail shutdown request. The paste
box supplies an optional command at 30M clocks. A configured write fault needs an
actual write workload before its effects can be assessed.

Runs finish paused, display the shared assertion results, and export the original
schedule, capture, metadata and report as an investigation bundle. Initial ROM
and disk inclusion remains explicit. Export after replay retains that completed
run's evidence, rather than subsequent interactive changes. Replay without
recorded checkpoint expectations is labelled accordingly.

The Pico1715 paired CLI runner preserves a fault-free control and optional bounded
command-reduction attempts. Browser fault runs currently contain one scenario;
paired browser control execution remains a follow-up. Reports separate a first
observed violation from a conclusive failure: downstream decoding uncertainty
must not turn a bad CRC observation into a claimed root cause. Neither the output
image nor simulation shutdown establishes physical SD durability.
